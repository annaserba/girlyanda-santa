# Гирлянда Тайного Санты

Русскоязычное приложение для новогоднего обмена подарками между коллегами.
Работает во внутренней сети: карта, справочник городов, значки и оформление
включены в проект и не требуют внешних сервисов.

## Возможности

- Регистрация по электронной почте и паролю, телефон РФ и город с поиском.
- Добровольная анкета: ФИО получателя (отчество при наличии), трек «Рядом» или «Страна», необязательные пожелания, площадка обязательна для «Рядом», смена — по желанию.
- Площадки с поиском и добавлением новых. Регистр букв не создаёт дубликаты; организатор может переименовывать и объединять площадки одного города.
- Отдельные локальные кольца и межгородское кольцо: каждый дарит и получает один подарок; подарки себе и взаимные пары запрещены.
- Личный кабинет с просмотром поданной анкеты, редактированием до жеребьёвки, её результатом и отметками об отправке и получении.
- Кабинеты организатора и координатора, импорт участников, контроль задержек и резервных подарков.
- Обезличенная карта на главной; `/garland` — карта организатора с ФИО, парами и статусами, доступная только администраторам.
- Общее письмо через `mailto:` и BCC. Отправляет пользователь из почтового клиента; приложение не подключается к SMTP и не подтверждает доставку.
- Название сайта, бюджет, сроки и публикация карты настраиваются организатором.

Создание аккаунта не подтверждает участие. Получатель определяется жеребьёвкой
организатора после сбора анкет; добавление новой анкеты не меняет ранее выданные результаты.
Для каждого кольца нужно минимум три совместимых участника.

## Загрузка в корпоративный GitLab

Частный архив содержит папку `.git`, историю коммитов и ветку `main`.
В нём `origin` уже настроен на корпоративный GitLab по SSH. После распаковки
откройте терминал в корне проекта и проверьте адрес:

```sh
git remote -v
git log --oneline -5
git ls-remote origin
```

Для отправки кода в пустой репозиторий:

```sh
git push -u origin main
```

Если код получен из публичного GitHub или используется другой проект GitLab,
скопируйте SSH-адрес из **Clone → SSH** в целевом проекте и настройте `origin`:

```sh
git remote set-url origin "SSH_URL_ИЗ_GITLAB"
git ls-remote origin
git push -u origin main
```

Замените `SSH_URL_ИЗ_GITLAB` полным адресом, включая нестандартный порт,
если он указан в GitLab. Для SSH публичный ключ компьютера нужно добавить
в **GitLab → SSH keys**; подробности — в [инструкции GitLab](https://docs.gitlab.com/user/ssh/).
При первом подключении сверяйте отпечаток ключа сервера с данными GitLab или ИТ.

- Тайм-аут подключения: проверьте корпоративную сеть/VPN и доступ к SSH-порту.
- `Permission denied (publickey)`: проверьте выбранный SSH-ключ и доступ пользователя к проекту.
- Ошибка HTTPS-сертификата: проверьте `git remote -v`, чтобы убедиться, что выбран нужный SSH-адрес.

Рабочий `.env` и `deployment/private/admins.sql` игнорируются Git.
Они передаются на сервер отдельно или через защищённые настройки CI.

## Установка сервера из частного архива

Нужны Linux, Docker Engine и Docker Compose v2. Node.js и npm на сервере
устанавливать не требуется: сборка выполняется внутри Docker.
В архиве находятся исходники и история Git; готовые Docker-образы не включены.

Сохраните включённые `.env` и `deployment/private/admins.sql`.
Файл `.env.example` используется для новой установки без готовых настроек;
поверх рабочего `.env` его копировать не нужно.

Из корня распакованного проекта выполните:

```sh
sh deployment/install-server.sh http://SERVER:3003
```

Замените `SERVER` внутренним DNS-именем или IP сервера. Порт должен совпадать
с `APP_PORT` в `.env` (в подготовленном архиве — 3003). Если настроен
HTTPS-прокси, передайте его адрес вместо прямого адреса с портом.

Установщик соберёт приложение, создаст PostgreSQL и применит миграции.
В пустую базу он перенесёт пять администраторов с прежними почтами, ролями
и хешами паролей, затем запустит приложение. Рабочие анкеты, сессии и результаты
жеребьёвки не переносятся. После входа проверьте название, правила и сроки.
Повторный запуск сохраняет существующие аккаунты и данные базы.

Машине сборки нужен доступ к npm, Docker-реестру и Alpine либо к их
корпоративным зеркалам. Если серверу npm недоступен, сборку выполняет CI-runner;
установщик поддерживает получение его результата из registry.
Полные команды и параметры приведены в [инструкции установки на сервер](docs/server-install.md).

## Новая локальная установка из публичного Git

Для этого варианта нужны Docker и Docker Compose. Создайте `.env`, если его ещё нет:

```bash
if [ ! -f .env ]; then cp .env.example .env; fi
openssl rand -hex 24
openssl rand -base64 32
```

Первую случайную строку сохраните в `POSTGRES_PASSWORD`, вторую — в
`BETTER_AUTH_SECRET` внутри локального `.env`. Заполните `ADMIN_EMAIL` адресом
организатора и задайте одинаковые `BETTER_AUTH_URL` и `NEXT_PUBLIC_APP_URL`.
Для локального запуска подойдёт `http://localhost:3000`.

```bash
docker compose up -d --build
```

Приложение откроется на [localhost:3000](http://localhost:3000).
Миграции выполняются при старте; PostgreSQL хранит данные в Docker volume.
Порты по умолчанию доступны только на локальном компьютере.
Для других портов задайте `APP_PORT` и `POSTGRES_PORT` в `.env`.

В новой базе без переноса администраторов зарегистрируйте организатора первым,
до открытия доступа участникам:
первый аккаунт автоматически получает права администратора.
Адрес из `ADMIN_EMAIL` также получает эту роль при регистрации.
Подтверждения владения почтой в этой версии нет.

Для работы в сети настройте адрес, HTTPS и доступ через внутренний прокси.
Задайте адрес в `BETTER_AUTH_URL` и `NEXT_PUBLIC_APP_URL` до запуска.
Вход и ссылки в браузере используют текущий сайт; готовый образ можно перенести
на другой адрес без пересборки.
Сборка требует доступа к зависимостям либо заранее подготовленного внутреннего зеркала.
Готовый образ работает без доступа к интернету.

## Разработка и проверки

Нужны Node.js 22 и PostgreSQL. Установите зависимости через `npm ci`,
заполните `.env`, включая `DATABASE_URL` для вашей локальной базы, затем:

```bash
npm run db:migrate
npm run dev
npm run typecheck
npm test
npm run build
```

Интеграционные тесты изменяют данные только в отдельной базе с именем
`santa_verification`. Перед запуском `npm run test:db` укажите её в
`DATABASE_URL`; рабочую базу использовать нельзя.

GitHub Actions выполняет проверку типов, unit/SSR-тесты, интеграцию с PostgreSQL
и production-сборку. Корпоративный GitLab CI/CD с Helm, Vault и Argo CD описан
в [docs/cicd.md](docs/cicd.md); автоматическое развёртывание по умолчанию выключено.
