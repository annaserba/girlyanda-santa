# Развёртывание исходников из Git или частного архива

На сервере нужны Linux, Docker Engine и Docker Compose v2. Node.js и npm
на сервер устанавливать не нужно: приложение собирается внутри Docker.
В частном архиве находятся исходники, рабочий `.env` и
`deployment/private/admins.sql` для переноса пяти администраторов.
Готовых Docker-образов в архиве нет.

## Установка из архива с нуля

Распакуйте архив, перейдите в корень проекта и сохраните включённый `.env`.
Не заменяйте его файлом `.env.example`. Запустите:

```sh
sh deployment/install-server.sh http://SERVER:3003
```

Замените `SERVER` на доступное сотрудникам DNS-имя или IP. Порт должен
совпадать с `APP_PORT` в `.env` (в подготовленном файле — 3003).
Для корпоративного HTTPS-прокси, настроенного на этот порт, передайте его адрес:

```sh
sh deployment/install-server.sh https://santa.example.test
```

Установщик обновит адреса в `.env`, соберёт приложение из исходников,
создаст постоянный том PostgreSQL, выполнит миграции и восстановит пять
администраторов. Только после этого он запустит приложение для участников.
Используются прежние почты, роли и пароли. Переносятся хеши паролей;
рабочие сессии, анкеты, жеребьёвки и подарки не переносятся.
На новом сервере проверьте название, правила и сроки события в настройках.

Сборочной машине нужен доступ к npm, базовым образам Docker и Alpine
либо к их корпоративным зеркалам. При необходимости задайте в `.env`:
`NPM_REGISTRY`, `NODE_IMAGE`, `ALPINE_MIRROR` и `SANTA_POSTGRES_IMAGE`.
Без доступа к этим источникам сборка из кода не выполнится.

## Развёртывание через Git/CI

В публичный Git входят код, Dockerfile, конфигурации CI/CD и установщик.
Рабочий `.env`, SQL-файл администраторов и пароли в Git не входят.
После клонирования передайте `.env` отдельно, а SQL — файлом на сервер
или через защищённую файловую переменную CI `SANTA_ADMIN_BOOTSTRAP_FILE`.
Путь должен быть доступен машине, выполняющей установщик.

Если npm недоступен серверу, сборку выполняет CI-runner с доступом к
корпоративному npm-зеркалу. Runner публикует результат в registry,
а сервер получает его оттуда:

```sh
SANTA_INSTALL_MODE=registry \
SANTA_APP_IMAGE=registry.example.test/team/girlyanda-santa:COMMIT_SHA \
sh deployment/install-server.sh https://santa.example.test
```

Доступы к registry задаются средствами Docker/платформы. Серверу в этом
режиме нужны registry и PostgreSQL-образ, а доступ к npm не требуется.

GitHub workflow выполняет проверки и сборку. Корпоративный GitLab pipeline
собирает код с переменными зеркал и разворачивает через Helm/Argo CD
после настройки платформы; детали — [cicd.md](cicd.md).
Для Kubernetes первоначальный SQL выполняют в новой PostgreSQL до открытия
доступа к приложению. SQL откажется работать в непустой базе и выполняется
одной транзакцией. Настройки Vault, registry, namespace и доступы CI нужно
задать в целевой организации; архив не содержит этих доступов.

## Повторный запуск

Повторите команду установщика. Аккаунты и том сохранятся, повторный импорт
в непустую базу пропускается. После первого успешного импорта SQL-файл
для последующих обновлений уже не требуется.
Смена адреса не требует пересборки: вход, QR-код и ссылки писем используют
текущий сайт; серверные ссылки используют `BETTER_AUTH_URL`.

Для проверки состояния:

```sh
docker compose --env-file .env --project-directory . -f deployment/server-compose.yml ps
docker compose --env-file .env --project-directory . -f deployment/server-compose.yml logs --tail=50 app
```

PostgreSQL не публикуется в сеть. Приложение слушает `APP_PORT` на всех
интерфейсах; DNS и доступность порта обеспечивает серверная сеть.
Для прокси на том же сервере задайте `SANTA_BIND_ADDRESS=127.0.0.1`.
Том `girlyanda-santa_pgdata` хранит данные сервера; его удаление удалит
аккаунты, анкеты и результаты. Обычный `docker-compose.yml` в корне
оставлен для разработки, серверный запуск выполняет установщик выше.

## Почта

Перенос администраторов не подключает SMTP. Рассылка по-прежнему формирует
одно письмо с BCC для ручной отправки из корпоративного почтового клиента.
